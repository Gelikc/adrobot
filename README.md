# Adrobot

Работающее веб-приложение по тестовому заданию Adrobot: **FastAPI + SQLAlchemy + React / TypeScript**. PostgreSQL — для Docker, SQLite — для быстрого локального запуска. Включены Alembic, серверный адаптер Keitaro Admin API v1 и отдельный постоянный демотрекер.

## Быстрый запуск без Docker

Нужны Python 3.14 и Node.js 22.12+ (проверено также на Node 25). Из папки проекта:

```powershell
python run.py
```

Команда создаёт виртуальное окружение, при необходимости устанавливает зависимости, применяет миграции, запускает оба сервера и открывает **http://127.0.0.1:5173**. Остановка — Ctrl+C в этом терминале. Порты 8000 и 5173 должны быть свободны. При изменении зависимостей установите их повторно по lock-файлам.

По умолчанию включён **деморежим без пароля**, рассчитанный на локальный компьютер. Данные сохраняются в `backend/adrobot.db`; обновление страницы и перезапуск не удаляют кампании, черновики и архив. Файл базы и секреты не входят в исходный архив.

Swagger UI: **http://127.0.0.1:8000/docs**. Нажмите **Authorize**, введите `Adrobot`: Swagger добавит `X-Requested-With: Adrobot` для изменяющих запросов. В рабочем режиме затем выполните `auth/login`. Пример curl приведён ниже.

### Раздельный запуск

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.lock
cd backend
..\.venv\Scripts\python.exe -m alembic upgrade head
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Во втором терминале из `frontend`:

```powershell
npm ci
npm run dev
```

## Запуск с PostgreSQL

При установленном Docker Desktop:

```powershell
docker compose up --build -d
```

Открыть **http://localhost:8080**. Compose запускает PostgreSQL, применяет миграции, ожидает готовности API и запускает Nginx с собранным React. База находится в volume `postgres_data`. `docker compose down` останавливает контейнеры с сохранением данных. Доступ наружу по умолчанию ограничен loopback компьютера.

Docker и PostgreSQL не были доступны на машине разработки: эта конфигурация подготовлена, но контейнерный запуск здесь не проверен. Локальный запуск, миграция SQLite, тесты и production-сборка frontend проверены.

## Что реализовано

- Создание кампании: название, страна GEO, поиск оффера с автодополнением, домен, группа, источник. Кампания сначала создаётся выключенной; после проверки двух потоков активируется.
- Первый поток направляет выбранную страну на Google; второй содержит выбранный оффер с долей 100%. Кампания использует обработку потоков по позиции.
- Импорт существующей кампании по ID, Fetch всех потоков и View in Keitaro.
- Потоки без офферов отображаются без редактирования их фильтров/редиректа.
- Add / Remove / Bring back; архив связей не удаляет сам оффер Keitaro.
- Черновик сохраняется на сервере. Keitaro изменяется только после Push. Cancel восстанавливает опубликованный состав и закрепления.
- Целые проценты, стабильное округление до суммы 100%; pin закрепляет текущую или введённую долю, остальные получают остаток поровну.
- При повторном Fetch внешне удалённые связи переходят в локальный архив. Fetch не затирает неопубликованный черновик.
- Проверка ревизий и внешнего снимка перед Push; защита от повторного Create/Push по Idempotency-Key.
- Журнал операций; сверка неопределённого результата после таймаута/перезапуска.
- Вход по серверному паролю оператора, сессии с HttpOnly-cookie, проверка Origin и заголовка изменяющих запросов, ограничение попыток входа.

## Сценарий проверки в браузере

1. Откройте предзагруженную кампанию **Beauty · Romania / Q4**, ID `93212`.
2. Нажмите «Добавить оффер», найдите `11112` и выберите результат. В редакторе будут четыре оффера по 25%; поток выделится жёлтым.
3. Откройте «Демотрекер»: там пока три оффера. Закройте окно и нажмите **Push to Keitaro** — теперь четыре и в демотрекере.
4. Удалите оффер и нажмите «Отменить»: состав вернётся. Повторите удаление и Push: строка останется в сером архиве. «Вернуть» и Push восстановят её.
5. Введите `25` в поле доли, нажмите галочку либо pin. Удаление/добавление остальных офферов не изменит закреплённые 25%.
6. В «Демотрекере» удалите оффер, имитируя правку напрямую в Keitaro. После Fetch связь появится в архиве редактора.
7. Для проверки конфликта сначала сделайте локальную правку, затем удалите другой оффер в демотрекере и нажмите Push. Внешние данные не перезапишутся. Отмените черновик, затем выполните Fetch.
8. Создайте новую кампанию через форму. Она появится в списке и в отдельном демотрекере с двумя потоками.

Демотрекер — отдельные записи в БД, а не подмена локального черновика. Он не обслуживает рекламные переходы посетителей. Реальные редиректы выполняет подключённый Keitaro, не FastAPI.

## Подключение настоящего Keitaro

Для Docker скопируйте `.env.example` в `.env` в корне проекта. Для локального Python — в `backend/.env`. Установите:

```dotenv
KEITARO_MODE=live
KEITARO_URL=https://your-tracker.example
KEITARO_API_KEY=your-admin-api-key
OPERATOR_PASSWORD=your-long-operator-password
FRONTEND_ORIGIN=http://127.0.0.1:5173
COOKIE_SECURE=false
```

Для Docker используйте `FRONTEND_ORIGIN=http://localhost:8080`. При размещении за HTTPS укажите реальный origin и `COOKIE_SECURE=true`. Для PostgreSQL со специальными символами в пароле URL-кодируйте их при составлении DATABASE_URL либо используйте URL-безопасный пароль.

Рекомендуется использовать **отдельную БД для live**, чтобы демонстрационные и реальные идентификаторы не пересекались. Например, для локальной проверки задайте `DATABASE_URL=sqlite+aiosqlite:///./adrobot-live.db`, затем примените миграции. Перезапустите backend после изменения окружения. Live-режим не запускается без HTTPS-адреса Keitaro, ключа и пароля длиной от 12 символов.

Keitaro должен разрешать читать кампании, потоки, офферы, домены, группы и источники и создавать/изменять кампании и потоки. API-ключ используется только сервером в заголовке `Api-Key`. Браузеру ключ не передаётся.

Адаптер написан по публичной [OpenAPI-схеме Admin API v1](https://admin-api.docs.keitaro.io/openapi.json) и [документации Keitaro](https://docs.keitaro.io/en/development/admin-api.html), проверенным 19.11.2026. Версия публичной схемы: `v1`. Создание: `POST /campaigns`, `POST /streams`; обновление офферов: `PUT /streams/{id}` с единственным полем `offers`; справочники: `/domains`, `/groups?type=campaigns`, `/traffic_sources`, `/offers`.

Публичная схема StreamRequest не описывает `action_payload`, хотя поле присутствует в ответе Stream и необходимо для URL редиректа. В адаптере передаётся `action_payload: "https://google.com/"`. Совместимость этого поля, типов `country`/`http`, потоков `regular`, прямого перехода через оффер при `schema=landings` и поведения нулевых долей нужно подтвердить на **конкретной установленной версии**. Создание проверяет прочитанные настройки до успешного результата. Если версия API отличается, правки локализованы в `app/keitaro.py` и `resume_create` в `app/services.py`.

**Реальный экземпляр и ключ в задаче не предоставлены.** Записи в настоящий Keitaro и фактическая GEO-маршрутизация ещё не проверены. Перед рабочим трафиком выполните интеграционную приёмку на тестовом экземпляре: создание → проверка двух потоков → симуляция разных стран → Add/Push → Remove/Push → Fetch внешнего изменения.

## Доли и состояния

При остатке `R` и `N` незакреплённых офферов каждый получает `R // N`; первые `R % N` по сохранённому порядку получают ещё 1%. Примеры: три оффера — 34/33/33; закреплённые 25% и два свободных — 25/38/37. Импорт сохраняет реальные доли без автоматического выравнивания.

Нельзя удалить последний активный оффер, превысить 100% закреплений или оставить все офферы закреплёнными с суммой, отличной от 100%. При удалении закрепление снимается; Cancel восстанавливает прежнее. Сумма pin=100% допускает свободные офферы с 0%; совместимость с целевой версией проверяется отдельно. Отключённая во внешнем Keitaro связь сохраняет `state=disabled`, а не молча включается при Push; её статус подписан в строке.

Fetch является транзакционным для локального состояния. Архив сохраняется. Недоступность или ошибочный формат ответа не превращаются в удаление связей.

## Операции и восстановление

Запись операции фиксируется до отправки внешних изменений. При таймауте, ошибке проверки либо аварийном завершении результат может иметь статус «Нужна сверка». Откройте **Операции → Сверить**. Незавершённый Push блокирует соответствующий поток.

Сверка Push сравнивает полный контрольный снимок с ожидаемым результатом: либо подтверждает публикацию, либо возвращает неизменившийся черновик для нового Push, либо сообщает конфликт. Сверка создания находит кампанию по уникальному alias `adrobot-…` и проверяет/достраивает потоки. Если результат начатого неидемпотентного POST нельзя однозначно найти, повторная запись не выполняется вслепую. Проверьте кампанию вручную в Keitaro и повторите сверку позже; автоматического удаления внешних сущностей нет.

Если после таймаута создания кампания так и не появилась, можно создать новую операцию после ручной проверки отсутствия исходной кампании; неопределённая старая запись остаётся в журнале. Эта ситуация не маскируется под успешный результат.

В этой версии поддерживается **один процесс backend / один Uvicorn worker**, общий черновик на поток и один пароль операторского контура. Изменяющие действия сериализуются внутри процесса. Несколько backend-реплик требуют распределённой блокировки/очереди операций и отдельной доработки. Во внешнем API нет используемой условной записи: не редактируйте один поток одновременно здесь и в админке Keitaro. Между проверкой снимка и записью остаётся окно конкурентного изменения.

## Тесты и сборка

Из `backend`:

```powershell
..\.venv\Scripts\python.exe -m pytest -q
..\.venv\Scripts\python.exe -m alembic check
```

Из `frontend`:

```powershell
npm run build
```

Проверяются сценарии редактора, архив, отмена, pin, внешние удаления, ревизии, идемпотентность, потерянный ответ после применения Push, авторизация/CSRF и HTTP-контракт Keitaro. Тесты используют отдельную временную SQLite-базу, не изменяют вашу демобазу и не ходят в настоящий Keitaro. Проверку PostgreSQL следует повторить в целевой среде.

Зависимости фиксированы в `backend/requirements.lock` и `frontend/package-lock.json`. `requirements.txt` задаёт допустимые диапазоны для обновления lock-файла. После смены версий необходимо повторить проверки.

## Пример REST-запроса

В деморежиме без авторизации:

```bash
curl -X POST http://127.0.0.1:8000/api/v1/campaigns \
  -H 'Content-Type: application/json' \
  -H 'X-Requested-With: Adrobot' \
  -H 'Idempotency-Key: example-create-0001' \
  -d '{"name":"Australia launch","geo_code":"AU","offer_id":4821,"domain_id":1,"group_id":1,"traffic_source_id":1}'
```

Ответ — объект операции со статусом и ID кампании при успехе. Код 202 означает, что нужно смотреть `status`, а не считать операцию автоматически успешной. Вход через API: `POST /api/v1/auth/login` с `{"password":"…"}` и тем же служебным заголовком; cookie сессии нужно сохранять между запросами.
